# PRD — XRLDB

## 产品目标

提供一个**兼容 Redis 生态、但提供强一致性保证**的分布式键值数据库，让「把 Redis 当作可靠存储」这件事第一次变得安全。

具体而言，三个可衡量的目标：

1. **兼容性**：任何现成的 Redis 客户端，不做任何代码改动即可连接使用
2. **一致性**：任意单节点故障（含 `kill -9`）后，已确认的写入一个不丢
3. **可配置性**：单个配置文件描述整个集群拓扑；沿用 Redis 的运维可直接复用现有 `redis.conf`

## 用户与使用场景

### 目标用户

| 用户 | 场景 |
|---|---|
| 从 Redis 迁移的团队 | 业务已把 Redis 当可靠存储用，担心故障丢数据，但不想改客户端代码 |
| 中小规模自建集群的团队 | 需要强一致，但 TiKV / CockroachDB 的运维复杂度与资源开销过重 |
| 学习分布式共识的开发者 | 希望有一个可完整阅读、能真实跑起来的三节点 Raft 实现 |

### 典型场景

**场景一：订单状态存储**
团队用 Redis 存订单状态。某次主节点故障切换，几十笔已确认的订单消失，引发对账问题。迁移到 XRLDB 后，客户端代码不变，但故障转移不再丢写。

**场景二：分布式锁与协调**
现有 Redis 方案依赖 Redlock，而 Redlock 在故障转移时存在竞态。XRLDB 的 Raft 语义天然提供单调递增的日志索引，可在此基础上构建正确的分布式锁。

**场景三：本地三节点实验**
开发者用一条命令拉起三节点集群，`kill -9` 掉 leader，观察重新选举与数据完整性。

## 核心问题

> **为什么现有的 Redis 兼容方案都不能提供强一致性？**

因为一致性不是可以「后来加上」的功能，它决定了架构地基：

- Redis Cluster 采用异步复制。主节点确认写入后立即返回，副本在后台追赶。主节点故障时，未同步的写入永久丢失。
- 要保证不丢，写入必须等到**多数派确认**才能返回——这需要共识协议（Raft / Paxos），而共识会引入一次额外的网络往返延迟。
- 这是一笔明确的交易：**用约 1ms 的写入延迟，换取「永不丢数据」**。XRLDB 选择做这笔交易。

反过来说，如果用户要的只是缓存，那么这笔交易不划算——这也正是 Redis 依然合适的地方。XRLDB 不试图取代 Redis 的缓存用途，而是覆盖 Redis 力所不及的可靠存储用途。

## 功能及其意义

| 功能 | 解决什么 | 为什么需要 |
|------|----------|------------|
| RESP3 协议兼容 | 客户端迁移成本 | 生态是这个项目存在的前提。不能兼容，用户就不会来 |
| Raft 强一致性 | 故障时丢数据 | 这是相对 Redis Cluster 的**唯一核心差异点** |
| 写请求透明转发 | 客户端需要感知集群拓扑 | Redis Cluster 要求客户端实现槽位路由；XRLDB 让任意节点都能接受写入，客户端无感 |
| TOML 配置 | 集群拓扑表达 | 嵌套结构（节点列表、各阶段超时）用类型安全的格式表达 |
| `redis.conf` 兼容 | 运维迁移成本 | 沿用 Redis 的运维可直接复用现有配置文件，零学习成本 |
| 快照与日志截断 | 日志无限增长 | 不截断则磁盘必然写满；截断则需要快照作为新的起点 |
| 故障注入测试 | 「不丢数据」的承诺无法自证 | 一致性必须能被**证明**，而不是被相信 |

## 功能之间的关系

```
          RESP3 协议兼容（前提）
                  │
     ┌────────────┴────────────┐
     │                         │
  读写命令                  管理命令
     │                         │
  写入必须经共识 ────► Raft 强一致性（核心差异点）
     │                         │
     └────────┬────────────────┘
              │
        存储与快照
              │
     ┌────────┴────────┐
     │                 │
  TOML 配置      redis.conf 兼容（都是「便于配置」的实现）
```

关键依赖关系：

- **协议兼容是一切的入口**。没有它，其他能力都无人使用。
- **强一致性是唯一的核心差异点**。如果去掉它，XRLDB 就退化成「又一个 Redis 克隆」，失去存在理由。
- **配置能力是辅助而非核心**。它降低成本，但不构成用户选择 XRLDB 的决定性理由——不能为它牺牲核心能力。

## 范围与非目标

### 范围（首版）

**命令**

```
连接:   PING  ECHO  QUIT
写:     SET（含 EX/PX/NX/XX）  GET  DEL  EXISTS
        MSET  MGET  APPEND  STRLEN
        INCR  DECR  INCRBY  DECRBY
键管理: EXPIRE  TTL  PERSIST  KEYS  SCAN  TYPE
服务器: INFO  DBSIZE  FLUSHDB
集群:   CLUSTER INFO
        RAFT LEADER / RAFT INFO / RAFT ADD-NODE
```

**能力**

- 单 Raft 组强一致（3 节点容忍 1 台故障）
- follower 上的写请求透明转发
- TOML 与 `redis.conf` 双格式配置
- 快照与 Raft 日志截断
- 本地三节点启停与故障验证脚本

### 非目标（首版明确不做）

- **分片 / 多 Raft 组**：单 Raft 组的写吞吐受单 leader 限制。分片是下一阶段的事，但当前架构必须为它留出泛化空间
- **Hash / List / Set / ZSet**：数据模型扩展，不影响核心正确性，可后置
- **AUTH 与访问控制**：默认只监听 `127.0.0.1`，对外暴露须显式改配置
- **`CONFIG GET/SET/REWRITE`**：Redis 运行时改配置的完整语义（尤其 `REWRITE` 的温和重写）
- **从 follower 读的降级模式**：牺牲一致性换吞吐，与项目定位冲突，需谨慎设计
- **自动化成员变更**：仅提供 `RAFT ADD-NODE` 手工入口

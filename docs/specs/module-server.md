# Spec — 网络服务层

## 要构建什么

- **目标**：接受 TCP 连接，把字节流交给协议层解析、交给后端执行，再把响应写回。
- **为什么需要**：这是客户端实际触达的入口。「官方 `redis-cli` 零改造可用」这条验收标准最终由这一层兑现。
- **位置**：
  - `src/server/listener.rs` — 监听与接受
  - `src/server/session.rs` — 单连接会话
  - `src/backend.rs` — 命令执行后端
  - `src/node.rs` — 按依赖顺序拼装各层

## 行为

### 职责边界

服务层**只关心「连接」与「字节」，不关心「命令的语义」**。命令语义全部委托给 `Backend`。

这条边界的存在理由很具体：接入 Raft 后，`Backend` 的内部会从「直接写本地状态机」变成「提交到共识层并等待多数派确认」，而**服务层一行都不用改**。

### 并发模型

每条连接一个 tokio 任务。单个连接阻塞或缓慢不影响其他连接。

状态机用 `RwLock` 保护：读命令之间可并发，写命令独占。连接级状态（协议方言）属于 `Framed` 的编解码器，天然随任务隔离。

### 两种错误的处理

| 错误 | 处理 |
|---|---|
| 命令层面（未知命令、参数不合法） | 回复错误文本，**连接继续** |
| 帧层面（字节流失去对齐） | 断开这一条连接，其他连接不受影响 |

### 会话生命周期

```
建立连接 → 循环 { 读命令 → (HELLO 则切换方言) → 执行 → 写回复 }
        → 直到 QUIT / 客户端断开 / 帧层面错误
```

`HELLO` 的方言切换必须发生在**生成回复之前**，否则 `HELLO` 自己的回复就会用错方言。

### 套接字选项

新连接一律设置 `TCP_NODELAY`。本协议的请求与响应都很小，等待攒满一个 MSS 再发送会显著增加往返延迟。

## 输入 / 输出

- **输入**：TCP 字节流
- **输出**：TCP 字节流

### CLI

```
xrl-db [选项]

  -c, --config <FILE>    配置文件路径（另有 XRLDB_CONFIG 环境变量）
      --listen <ADDR>    覆盖监听地址（另有 XRLDB_LISTEN）
      --node-id <N>      覆盖节点 ID（另有 XRLDB_NODE_ID）
      --check            只校验配置并退出，不启动服务
  -h, --help
  -V, --version
```

## 约束

- **不得**让任何单条连接的异常影响其他连接或导致进程退出。
- **不得**在服务层引入命令语义——它不认识 `GET`、`SET` 的含义。
- 锁中毒时**必须**恢复数据继续服务，而不是让整个数据库倒下。
- `accept` 失败**不得**终止接受循环（通常是文件描述符暂时耗尽这类一过性问题）。
- 写回复**必须**按发出命令时的方言编码。
- **不得**在可预期的错误路径上 `unwrap()`。

## 边界条件

| 情况 | 行为 |
|---|---|
| 客户端发送未知命令 | 回复 Redis 风格错误，连接继续 |
| 客户端发送垃圾字节 | 帧层面错误，断开该连接，其他连接不受影响 |
| 客户端发送 `QUIT` | 先回复 `OK`，再关闭连接 |
| 客户端连发多条命令（流水线） | 逐条读取、逐条回复，顺序严格对应 |
| 客户端一次只发半个命令 | 等待剩余字节，不报错 |
| `accept` 返回错误 | 记录后继续接受 |
| 收到 `Ctrl-C` | 打印提示并优雅退出 |
| 端口被占用 | 启动失败，退出码非零，错误信息包含具体地址 |

## 关于 `INFO` 的两个有意的设计

1. **`cluster_enabled` 恒为 `0`**（即使配置了多节点）。Redis 客户端看到它为 `1` 会启用**槽位路由**并对 `MOVED` 重定向做特殊处理，而本项目是单 Raft 组、不做分片，服务端会自行把请求转到 leader。报 `0` 才能让客户端保持最简单的行为。真实的集群拓扑由非标准的 `xrldb_*` 字段如实告知。

2. **提供 `redis_version` 字段**。不少客户端读取它来决定启用哪些特性，缺失会导致行为异常。同时提供 `xrldb_version` 表明真实身份。

## 验收标准

- [x] `SET` / `GET` 往返正确，缺失键返回空值
- [x] 未知命令返回错误后**连接仍可用**
- [x] 参数个数错误后连接仍可用
- [x] 值二进制安全（含 CRLF 的值长度正确、内容原样）
- [x] 流水线命令的回复严格对应顺序
- [x] 内联命令被接受
- [x] 内联命令被 TCP 切开时不断连
- [x] `HELLO 3` 后空值编码由 `$-1\r\n` 变为 `_\r\n`
- [x] `HELLO 3` 返回 RESP3 原生映射（`%`）而非降级为扁平数组
- [x] `TTL` 三种返回值正确
- [x] 键真的会过期（`EXISTS` / `TTL` 随之变化）
- [x] `SET NX` 不覆盖已有值
- [x] 数组回复的 framed 正确，缺失元素占位为 null
- [x] 多条连接共享同一个状态机
- [x] `DBSIZE` 只统计未过期的键
- [x] `QUIT` 先回复再关闭连接

## 端到端验证（非自动化，但已手工执行）

用**官方 `redis-cli 8.8.1`** 实测通过：

```
$ redis-cli -p 7799 SET foo bar   → OK
$ redis-cli -p 7799 GET foo       → "bar"
$ redis-cli -3 -p 7799 PING       → PONG          （RESP3 模式）
$ printf 'PING\r\n' | nc 127.0.0.1 7799            （内联命令）
+PONG
```

## 已知限制

- 数据**不落盘**：当前为纯内存实现，进程退出即丢失。持久化随共识层一同引入。
- **共识层尚未接入**：集群配置能被加载，但节点之间不通信，也不提供强一致性。
- 无连接数上限、无空闲超时、无 `maxclients` 限制。

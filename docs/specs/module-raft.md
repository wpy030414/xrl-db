# Spec — 共识层与客户端转发

## 要构建什么

- **目标**：让一份写入在多数派节点确认之后才对客户端可见；让客户端连到**任意**节点都能读写，且在失去多数派时如实拒绝而不是返回可能过期的数据。
- **为什么需要**：这是项目定位的落点。「兼容 Redis 生态」由协议层兑现，「提供 Redis 拿不到的强一致性」由这一层兑现——少了它，项目就只是又一个 Redis 兼容实现。
- **位置**：
  - `src/raft/types.rs` — `TypeConfig`（日志条目是 `WriteOp`，状态机返回 `Reply`）
  - `src/raft/log_store.rs` — `RaftLogStorage` / `RaftLogReader`
  - `src/raft/state_machine.rs` — `RaftStateMachine` / `RaftSnapshotBuilder`
  - `src/raft/rpc.rs` — 节点间线路协议与服务端
  - `src/raft/network.rs` — 节点间 RPC 的客户端侧
  - `src/raft/forward.rs` — 把客户端请求转交给主节点
  - `src/node.rs` — 拼装

## 行为

### 写路径

```
Backend → Node::write(WriteOp) → Forwarder
                                    │
              第 0 次尝试永远在本地做 ──► 是主节点就直接提交，否则拿到主节点提示
                                    │
              后续尝试转发给主节点 ──► leader 的 dispatch → client_write
                                    │
                          多数派确认后才返回 Reply
```

`Node::write` 返回时，写入**已经存在于多数派节点上**。这是「不丢数据」承诺的物理兑现点。

### 读路径（ReadIndex）

```
Backend → Node::read(f) → Forwarder::read_index()
                              │
            主节点：ensure_linearizable() ──► 返回 read_log_id
            从节点：向主节点要一个它刚确认过的日志位置
                              │
                   等待本地状态机追平该位置（超时则拒绝）
                              │
                    在本地状态机上执行 f
```

读**不搬运数据**。从节点只需一次极小的 RPC 往返，随后完全本地读取。

### 重试判据

| 情况 | 能否证明未生效 | 处置 |
|---|---|---|
| 连接就建立不起来 | 能——请求根本没发出去 | 重试 |
| 主节点回复 `ForwardToLeader` | 能——写入从未进入日志 | 重试 |
| 主节点回复成员变更错误 | 能 | 重试 |
| 请求已发出但超时 / 连接中断 | **不能** | 立即返回「结果未知」 |
| 处理请求的节点在回复前停止 | **不能** | 立即返回「结果未知」 |
| 本节点失去多数派，提交迟迟不返回 | **不能** | 限时后返回「结果未知」 |

「结果未知」是一条**必须原样传给客户端**的错误。它不是「失败」的同义词，绝不可据此自动重试。

### 失去多数派时的行为

| 操作 | 行为 |
|---|---|
| 写 | 拒绝，并且在限时内返回（不能永远挂住） |
| 读（主节点） | 拒绝（`ensure_linearizable` 报 `QuorumNotEnough`） |
| 读（从节点） | 拒绝（找不到主节点，拿不到读索引） |

这是 CP 语义：宁可不可用，也不返回可能过期的数据或接受可能被回滚的写入。

### 集群组建

| 场景 | 行为 |
|---|---|
| 单节点部署（未启用集群，或 peers 只有自己） | 自动自举，无需任何开关 |
| 一个节点带 `--bootstrap` | 自举成单节点集群，再把 `cluster.peers` 里的其他节点逐个纳入 |
| 不带 `--bootstrap` 的节点 | 只启动，等待被纳入。**绝不自举** |
| 数据目录已有内容 | `--bootstrap` 幂等：沿用磁盘上的成员配置继续启动 |
| 某个配置里写明的节点始终起不来 | 引导节点**启动失败**，而不是降级成更小的集群 |

### 快照与日志截断

- 累计 `snapshot_logs_since_last` 条日志后生成一次快照
- 快照点之前的日志被截断，保留 `max_in_snapshot_log_to_keep` 条
- 日志**只能靠快照截断**：没进快照的日志不允许删除

## 输入 / 输出

- **输入**：`WriteOp`（写）/ 一个只读闭包（读）/ 节点间 RPC 消息
- **输出**：`Reply`；失败时为 `NodeError`（含 `ForwardError`）

## 约束

1. **状态机的 apply 必须确定性**。日志里存的必须是绝对时刻，不能有相对时间——同一份日志在不同副本上重放必须得到完全相同的结果。
2. **`applied_state` 只与快照一起持久化**，绝不单独写入。两者一旦分裂，重启后就会丢失或重复应用。
3. **节点间 RPC 必须能区分「对方明确拒绝」与「网络不通」**。前者可能意味着写入没有生效（可重试），后者不能。
4. **节点地址优先取自静态配置，取不到时退回 Raft 成员信息**。`network.rs` 与 `forward.rs` 必须采用同一策略。
5. **关闭节点必须释放 RPC 端口与 redb 文件锁**。RPC 服务循环持有监听器和一份 `Raft` 引用，必须能被显式停止。
6. **redb 是单进程的**。每个节点必须使用独立的 redb 文件。

## 边界条件

| 情况 | 期望行为 |
|---|---|
| 集群尚未选出主节点 | 短暂等待并重试（约几百毫秒），随后返回明确错误 |
| 主节点在转发途中换届 | 依据对方给出的提示重试，客户端无感 |
| 主节点被 `kill -9` | 剩余节点在秒级内选出新主节点；已确认的写入一个不丢 |
| 请求已发出但响应丢失 | 返回「结果未知」，**不重试** |
| 孤立的主节点收到写请求 | 限时后返回「结果未知」，**不永远挂住** |
| 从节点落后于主节点 | 等待追平；超时则拒绝本次读 |
| 日志为空 | 读索引为 `None`，直接本地读（没有任何已提交数据） |

# DECISIONS

记录重大设计抉择背后的原因，防止架构漂移。每条决策回答：为什么这样做？当时考虑过什么替代方案？

## ADR-001：项目定位为「兼容 RESP3 的强一致集群键值数据库」

- **日期**：2026-09-26
- **状态**：已采纳
- **背景**：在数据库领域立项，首先要回答的是「做什么」。关系型数据库赛道有 SQLite 与 PostgreSQL 这样经过数十年积累的对手；缓存赛道有 Redis 本身；分布式强一致存储赛道有 TiKV 与 CockroachDB，但它们对中小规模自建集群而言，运维复杂度与资源开销都偏重。
- **考虑过的方案**：
  1. 关系型数据库（SQL）
  2. 键值数据库，兼容 Redis 生态，但不提供一致性保证
  3. 键值数据库，兼容 Redis 生态，并提供 Raft 强一致性
- **决策**：方案 3。做「兼容 Redis RESP3、提供 Raft 强一致性」的集群键值数据库，实现语言选用 Rust。
- **为什么选这个**：方案 3 占据了一个**具体的、可被验证的空白**——Redis 生态的兼容性与强一致性从未被同时满足。Redis Cluster 的官方文档自承不提供强一致性保证：它使用异步复制，主节点故障切换时，尚未同步到副本的写入会永久丢失。这意味着「把 Redis 当作可靠存储」始终是一件有风险的事。而兼容 RESP3 意味着现有 Redis 客户端零改动即可使用，迁移成本接近于零。这个组合的收益明确，且不需要与任何人正面竞争。
- **为什么不选其他**：方案 1 的竞争壁垒是数十年的工程积累与生态，正面竞争没有胜算；方案 2 是重复造一个更弱的 Redis，没有存在理由。语言选 Rust 是因为「高性能」是核心目标之一，需要无 GC 的运行时与对内存布局的控制力。
- **后果**：项目的一切后续决策（协议选择、一致性模型、存储选型）都以这个定位为准绳。任何削弱兼容性或削弱一致性保证的改动都应当被质疑。
- **何时重新审视**：不适用——这是项目定位层面的决策。

## ADR-002：采用 Redis RESP3 协议兼容

- **日期**：2026-09-26
- **状态**：已采纳
- **背景**：新数据库需要一个客户端接入协议。从零设计一个自定义协议意味着同时要写 SDK、工具链和文档，而用户不会为了一个未经验证的数据库去学新协议。
- **考虑过的方案**：
  1. 自定义二进制协议（性能最优）
  2. HTTP / JSON（最易调试）
  3. Redis RESP3 协议兼容
- **决策**：方案 3。实现 RESP3 编解码，兼容官方 `redis-cli` 与各语言 Redis 客户端。
- **为什么选这个**：**协议兼容等于白捡整个生态**。`redis-cli`、各语言 SDK、连接池、监控工具全部零改动可用。对一个新项目来说，「无需改造现有代码」是降低迁移成本最有效的手段。协议本身也不复杂（十来种类型前缀）。
- **为什么不选其他**：方案 1 性能上限更高，但需要用户承担全量改造的成本，在没有生态的情况下几乎不可能被采用；方案 2 的每次请求解析开销与「高性能」目标直接冲突。
- **后果**：需要仔细处理 RESP3 的边界情况（二进制安全的 bulk string、inline command、协议错误恢复）。兼容性以官方 `redis-cli` 的行为为准绳。
- **何时重新审视**：若 RESP3 成为性能瓶颈（不太可能），或生态发生重大迁移。

## ADR-003：一致性模型采用 Raft（单 Raft 组）

- **日期**：2026-09-26
- **状态**：已采纳
- **背景**：既然要做「支持集群」，必须决定集群的一致性语义。这不是可以后加的特性——它决定架构地基。
- **考虑过的方案**：
  1. **单 Raft 组**：全部数据一份日志，leader 统一接受写入，多数派确认后提交（CP）
  2. **主从异步复制**：primary 立即返回，后台推给副本（实现最简，故障会丢数据）
  3. **Gossip 最终一致**：无主、向量时钟、读写仲裁（AP，Dynamo 风格）
  4. **分片 + 每片一个 Raft 组**：同时获得水平扩展与强一致（TiKV 路线，实现量最大）
- **决策**：方案 1（单 Raft 组）。方案 4 作为下一阶段的演化目标。
- **为什么选这个**：强一致性是本项目相对 Redis Cluster 的**唯一核心差异点**，是不可让步的。方案 2 恰恰复制了 Redis Cluster 的缺陷，会让项目失去存在理由。方案 4 虽然最终目标更优，但实现量约为方案 1 的 3–5 倍（多 Raft 组、分片元数据、槽位迁移），一步到位风险过高。
- **为什么不选其他**：方案 2 会丢数据；方案 3 放弃强一致，同样背离定位；方案 4 的实现量会让项目在完成核心能力前就陷入停滞。
- **后果**：
  - 写入延迟增加一次网络往返（同机房约 0.5–2ms），这是换取「不丢数据」的明确代价
  - 写吞吐受单 leader 限制，数据量受单机内存限制
  - 但 Raft 内核在方案 4 中可以**原样复用**，当前工作不会浪费
- **何时重新审视**：当单 leader 的写吞吐或单机数据量成为实际瓶颈时，演化到方案 4。

## ADR-004：选用 openraft 实现 Raft

- **日期**：2026-09-26
- **状态**：已采纳
- **背景**：确认要做 Raft 后，需要决定是实现来源。手写 Raft 的典型失败模式不是「跑不起来」，而是「跑得起来但偶发选举错误或日志分歧，静默丢数据」——这类 bug 在单元测试中几乎不可见。
- **考虑过的方案**：
  1. **openraft**
  2. **raft-rs**（TiKV 所用）
  3. 手写
- **决策**：方案 1，openraft 0.9.25 稳定线。
- **为什么选这个**：决定性理由不是「有现成库」，而是 **openraft 自带协议一致性测试套件** `openraft::testing::Suite::test_all`——跑通即证明我们的存储实现满足 Raft 协议对存储的全部要求。这把「正确性」从「我们希望它是对的」变成「它被证明是对的」，直接消解了本项目最大的技术风险。
- **为什么不选其他**：
  - `raft-rs` 最新版停留于 0.7.0（2023-03-07），**两年半无更新**，且它是较底层的协议层，需要自己实现存储、网络与应用逻辑，上手成本并不比 openraft 低
  - 手写 Raft 意味着自己承担共识正确性的全部风险，且失去了上述测试套件
- **后果**：必须严格使用 openraft 0.9 的 API。0.9 已把旧的单一 `RaftStorage` 拆分为 `RaftLogStorage` + `RaftStateMachine`，网上大量教程（含官方 getting-started 页）仍是 0.8 写法，**照抄无法编译**。
- **何时重新审视**：若 openraft 停止维护，或出现 API 更合适的替代品。

## ADR-005：选用 redb 作为存储后端

- **日期**：2026-09-26
- **状态**：已采纳
- **背景**：Raft 需要可靠的本地持久化：日志必须在返回成功前落盘（`save_vote` / `append` 的持久性要求），状态机需要能被重建。
- **考虑过的方案**：
  1. **redb** 4.3.0
  2. **sled**（纯 Rust，曾是热门选择）
  3. **rocksdb**（rust-rocksdb）
  4. 自研 LSM-tree 或 Bitcask
- **决策**：方案 1，redb 4.3.0。Raft 日志与 KV 状态机共用一个 redb 实例的两张表。
- **为什么选这个**：`Durability::Immediate` 保证 commit 返回前数据已 fsync 到稳定存储，**这恰好就是 Raft 对日志持久化的硬性要求**，无需自己包装。纯 Rust 实现，无 C++ 工具链依赖。单写多读的事务模型与 Raft 的串行 apply 语义天然对齐。文件格式稳定并承诺升级路径。
- **为什么不选其他**：
  - **sled** 作者已将工作转向其他项目，1.0 长期停留在 alpha（最后发版 2024-10），且明确声明磁盘格式在 1.0 前会以需要手动迁移的方式变更；作者自己建议「若可靠性是首要约束，请用 SQLite」。磁盘格式会破坏性变更对一个数据库项目是硬伤
  - **rocksdb** 需要从源码完整编译 RocksDB 的 C++ 代码并运行 bindgen，依赖 libclang 与多个压缩库，构建负担过重，且引入大量 `unsafe` FFI
  - **自研存储引擎**等于从零实现崩溃一致性——这正是分布式数据库最常见的自伤点，与「不牺牲正确性」的原则直接冲突
- **后果**：
  - 接受明显的空间放大（redb 官方自报基准约 4 GiB vs RocksDB 893 MiB）
  - **redb 是单进程的**（文件锁），每个节点必须使用独立文件，多节点测试同样如此
  - 若将来需要更换后端，openraft 的 trait 边界使得替换是局部改动
- **何时重新审视**：若空间放大成为实际约束，或需要更高随机读性能。

## ADR-006：自研 RESP3 编解码

- **日期**：2026-09-26
- **状态**：**已废弃**（被 [ADR-011](#adr-011采用-redis-protocol-实现-resp3-编解码) 取代）
- **背景**：确定了 RESP3 兼容后，可选择现成 crate（如 `redis-protocol`）或自研编解码。
- **考虑过的方案**：
  1. 使用 `redis-protocol` crate
  2. 自研 RESP3 编解码
- **决策**：方案 2。
- **为什么选这个**：`redis-protocol` 最后发版为 2024-11-15，**已停滞近两年**。而 RESP3 编解码本身并不复杂（十来种类型前缀），却正是最需要控制内存分配的地方——零拷贝解析可以直接借用输入缓冲的 `&[u8]` 切片，避免为每个 key/value 分配 `String`。通用库未必针对这一点优化。
- **为什么不选其他**：引入一个停滞两年的依赖，等于把协议层的演进与修复能力交给了不确定的维护者，而自己实现的成本可控。
- **后果**：需要自己处理 RESP3 的边界情况（二进制安全、inline command、协议错误恢复），并用 `proptest` 做「编码 → 解析」往返一致性验证。若自研成本超出预期，替换回现成 crate 是模块边界内的局部改动。
- **何时重新审视**：若自研实现暴露出大量协议边界问题，维护成本超过预期。

## ADR-007：配置支持 TOML 与 redis.conf 双格式

- **日期**：2026-09-26
- **状态**：已采纳
- **背景**：「便于配置」是本项目的卖点之一。配置格式的选择直接决定这个卖点能否成立。
- **考虑过的方案**：
  1. 只用 TOML
  2. 只用 `redis.conf` 风格的行式 `key value`
  3. TOML 原生 + `redis.conf` 兼容层
- **决策**：方案 3。按扩展名分派解析器（`.toml` → TOML；其他 → 行式），解析后归一到同一个强类型 `Config` 结构体。
- **为什么选这个**：TOML 表达集群拓扑这类嵌套结构最为自然（TiKV 同样选择 TOML），且与 serde 无缝衔接、类型安全。而 `redis.conf` 兼容层让**沿用 Redis 的运维可以直接把现有配置文件拿过来用**——这是「便于配置」最硬的证据，迁移成本接近于零。
- **为什么不选其他**：方案 1 会让 Redis 运维面对一个陌生的配置格式；方案 2 用行式格式表达嵌套的 `peers` 列表需要发明自定义语法，可读性差。
- **后果**：需要维护两个解析器。配置优先级明确为 **CLI 参数 > 环境变量 > 配置文件 > 内置默认值**，并在文档中写明。
- **何时重新审视**：若双解析器带来持续的维护负担且实际使用率很低。

## ADR-008：follower 上的写请求采用服务端透明转发

- **日期**：2026-09-26
- **状态**：已采纳
- **背景**：单 Raft 组中只有 leader 能处理写入。当客户端连接到 follower 时，服务端必须作出选择。
- **考虑过的方案**：
  1. 返回错误，让客户端自己去找 leader
  2. 用 `MOVED` 重定向（Redis Cluster 的做法）
  3. 服务端透明转发到 leader
- **决策**：方案 3。
- **为什么选这个**：**对客户端完全透明**——它不需要知道集群拓扑，也不需要实现任何路由逻辑。这是相对 Redis Cluster 的一处额外优势：Redis 要求客户端实现 16384 槽位的路由与重定向处理，而 XRLDB 让客户端连任意节点都能写入。
- **为什么不选其他**：方案 1 把复杂度推给用户，体验差；方案 2 是分片场景的语义（「这个键不归我管」），而单 Raft 组中 follower 并非「不管」这些键，只是不能独自处理写入，用 `MOVED` 语义上不准确，且会强迫客户端实现重定向逻辑。
- **后果**：follower 需要维护到 leader 的连接并可转发请求，增加了网络层的复杂度；需注意转发链路的超时与错误传播。
- **何时重新审视**：引入分片后，`MOVED` / `ASK` 语义将变得必要，届时两者会共存。

## ADR-009：首版不实现认证，默认只监听回环地址

- **日期**：2026-09-26
- **状态**：已采纳
- **背景**：Redis 因默认无密码且监听全网卡，历史上造成过大量数据泄露事件。兼容 Redis 协议意味着可能继承同样的风险。
- **考虑过的方案**：
  1. 不实现认证，默认监听 `0.0.0.0`
  2. 不实现认证，但默认只监听 `127.0.0.1`
  3. 首版即实现 `AUTH` / `requirepass`
- **决策**：方案 2。
- **为什么选这个**：在**不增加实现工作量的前提下**消除了最大的安全风险——默认配置无法从外部访问。要对外暴露必须显式修改配置，这个动作本身就是一道提示。同时避免把认证机制的设计仓促塞进首版。
- **为什么不选其他**：方案 1 是有历史教训的反模式；方案 3 会增加配置分发与密钥管理的复杂度，而对一个尚未验证的原型来说并非当务之急。
- **后果**：`INFO` 命令应明确提示当前无密码且仅监听本机。文档需说明对外暴露时应当如何配置。
- **何时重新审视**：**在任何计划对外提供服务之前必须实现认证**。这是一个有时限的决策，不是永久豁免。

## ADR-010：文档模板采用 scaffold-docs 验收式标准

- **日期**：2026-09-26
- **状态**：已采纳
- **背景**：建立文档体系时需要选定模板。业界常见两套写法：「实现契约式」（specs 为「模块路径 + 依赖 + 类型签名代码块 + 关键行为 + 约束」，DECISIONS 为简化的三段式 ADR）与「验收式」（specs 为「要构建什么 + 行为 + 验收标准 + 完成定义」，DECISIONS 为含日期/状态/后果/重新审视时机的完整 ADR）。二者混用会造成文档风格漂移。
- **考虑过的方案**：
  1. 「实现契约式」模板
  2. 统一到 `scaffold-docs` skill 的「验收式」标准
- **决策**：方案 2。
- **为什么选这个**：`scaffold-docs` 是项目所有者的全局标准，适用于所有项目，统一标准优于各自为政。更重要的是，完整的 ADR 字段（尤其「何时重新审视」）能有效防止决策在失去上下文后被无意推翻——这个字段的价值远超格式本身。
- **为什么不选其他**：实现契约式的优势是 specs 更贴近代码（直接给出类型签名），但代价是 specs 与源码大量重复，源码一改文档就过时；且其 ADR 缺少「何时重新审视」，决策容易在人员更替后被无意推翻。
- **后果**：所有文档按 skill 模板编写；`docs/specs/` 随各模块的实现逐步填充，不凭空编造。
- **何时重新审视**：若全局标准本身发生变更。

## ADR-011：采用 redis-protocol 实现 RESP3 编解码

- **日期**：2026-09-26
- **状态**：已采纳（取代 [ADR-006](#adr-006自研-resp3-编解码)）
- **背景**：ADR-006 原本决定自研 RESP3 编解码，理由是 `redis-protocol` 最后发版于 2024-11-15、已停滞近两年，而 RESP3 编解码正处在最需要控制内存分配的热路径上。该决策做出后，针对 Rust 共识与协议生态的进一步调研给出了反驳证据，促成了这次反转。
- **考虑过的方案**：
  1. **维持自研**（ADR-006 原方案）
  2. **改用 `redis-protocol` 6.0**（本文档所采纳）
- **决策**：方案 2。引入 `redis-protocol` 6.0 与 `tokio-util`，使用其 `codec` 模块配合 tokio 的 `Framed`。
- **为什么选这个**：三条新证据改变了权衡。
  1. **协议已冻结**。「库的更新停滞」与「协议会变」是两回事——RESP3 规范不会再演进，因此停滞带来的风险远低于一般依赖。
  2. **该库的 `codec` 模块本身就是零拷贝的**，原先「自研才能控制内存分配」的论点不再成立。
  3. **该库有 927 万下载量，是事实标准**。内联命令、RESP2/RESP3 协商、push 消息等边界情况都已被大量生产使用验证过，自研等于重新踩一遍这些坑。
- **为什么不选其他**：自研方案的唯一优势是「完全控制」，但在节省下的时间可以直接投入到项目的**真正风险点——Raft 正确性**上的前提下，这个优势不足以支撑其成本。项目的关键路径是共识层，不是协议层。
- **后果**：
  - 依赖增加 `redis-protocol` 与 `tokio-util`
  - 该库为单维护者项目（2025-02 后无 push，71 stars），若出现协议层 bug 需自行 fork 修复——这是本决策明确接受的风险
  - 服务端的 I/O 形状将围绕 tokio-util 的 `Framed` 组织
- **何时重新审视**：若该库暴露出影响正确性的缺陷且无人修复，或在性能剖析中成为瓶颈。

> **附注（保留 ADR-006 的部分论据）**：调研中确认，作为**服务端**，请求侧的解析面比通用客户端库小得多——客户端只发送 bulk string 数组与内联命令，RESP3 的复合类型主要出现在我们自己编码的回复方向上。这一观察并不改变本决策（它只说明自研的成本比最初估计的更小），但值得记录，以防将来重新评估。同类项目 Kiwi（arana-db/kiwi）选择了自研 RESP 层，可作为反面参照。

## ADR-012：从节点直接读，读路径采用 ReadIndex 而非转发

- **日期**：2026-09-26
- **状态**：已采纳
- **背景**：ADR-008 决定把 follower 上的**写**请求转发给 leader，但当时没有说清**读**怎么办。最初的实现是读也走 leader（在 leader 上 `ensure_linearizable` 之后读本地）。这带来两个问题：一是所有读都汇聚到单个 leader，读吞吐不随节点数扩展；二是数据量大的值（比如几 MB）要为每次读在节点之间搬运一遍。
- **考虑过的方案**：
  1. 读也转发给 leader，在 leader 上确认领导权后读 leader 的本地状态
  2. 从节点读本地数据（放弃线性一致，可扩展但会返回旧值）
  3. **ReadIndex**：从节点向 leader 要一个「线性一致读索引」，等自己的状态机追平该索引后本地读取
- **决策**：方案 3。
- **为什么选这个**：方案 1 的正确性没问题，但把可扩展性白白丢掉了。方案 2 直接违反项目定位——返回可能过期的数据正是本项目要消灭的东西。方案 3 的代价只是一次小小的 RPC 往返（几个字节的日志位置），换取的是读完全在本地完成：数据不必搬运，读吞吐可以随节点数扩展。这是 Raft 论文里给出的标准做法，etcd 与 TiKV 都这么做。
- **为什么不选其他**：方案 2 不满足项目承诺，没有讨论余地。方案 1 的唯一优势是实现更简单，但那点简单换来的是「读吞吐被单个 leader 锁死」，在读写混合的负载下很快就会成为瓶颈。
- **后果**：
  - 从节点的读会多一次 RPC 往返，比直接读本地略慢；但避免了数据搬运，值越大越划算
  - 失去多数派时读会被**拒绝**而非降级——这是刻意的：无法确认时效性的读等于返回可能过期的值
  - 节点间 RPC 因此多了一个只承载「日志位置」的请求类型，它不涉及任何客户端命令，不引入跨层依赖
- **何时重新审视**：若读延迟成为主要抱怨点且负载以读为主，可以考虑 leader 租约（leader lease）省掉那次往返——代价是依赖时钟同步。

## ADR-013：转发失败后的重试判据是「能否证明未生效」，无法证明时报「结果未知」

- **日期**：2026-09-26
- **状态**：已采纳
- **背景**：写请求被转发到 leader 之后，如果响应在回程丢失，发起转发的节点面临一个无法回避的选择：重试，还是报错？这不是一个可以用「更健壮的重试策略」绕开的问题——**一次 `INCR` 被执行两次，与一次写入悄悄丢失，是两种不同性质的错误**，而不确定性本身无法被消除。
- **考虑过的方案**：
  1. **一律重试**：失败就重发，直到成功。简单、看起来健壮
  2. **一律不重试**：失败就报错
  3. **按「能否证明未生效」区分**：只重试那些**可以证明没有产生副作用**的失败；无法证明的，把不确定性原样告诉客户端
- **决策**：方案 3。
- **为什么选这个**：方案 1 与方案 2 都把「不确定」偷换成了「确定」，只是偷换的方向相反。方案 1 让客户端以为写丢了的写入重来一遍，`INCR` 于是多加一次；方案 2 让客户端对一条其实已经生效的写入重试，效果与方案 1 相同，而且它还会让那些**确实没生效**的写入白白失败。方案 3 承认不确定性存在，并按证据分类：
  - 连接根本没建立起来 → 请求没发出去 → **可重试**
  - leader 回复 `ForwardToLeader` → 写入从未进入日志 → **可重试**
  - 请求已发出但超时 / 连接中断 → **结果未知**
  - 处理请求的节点在回复前停止 → **结果未知**
  - 本节点失去多数派、提交迟迟不返回 → **结果未知**
- **为什么不选其他**：方案 1 会破坏数据（非幂等命令被重复执行），这比返回一个诚实的错误严重得多。方案 2 让「leader 刚好换届」这种纯瞬态也变成客户端可见的失败，可用性白白受损。
- **后果**：
  - 客户端可能收到一条措辞明确的「结果未知」错误。它在语义上不比 Redis 客户端连接被切断时更差，但因为多了一跳转发，发生概率更高
  - 本地提交也必须限时（否则失去多数派时会永远挂住），而限时之后同样落入「结果未知」
  - 彻底的解法是**请求去重**：客户端带请求号，服务端维护去重表，把「至少一次」变成「恰好一次」。这需要额外的状态与清理策略，首版不做
- **何时重新审视**：当「结果未知」成为实际运维投诉，或当客户端库开始要求幂等重试语义时，实现请求去重。

## ADR-014：集群由一个显式指定的节点组建，其余节点绝不自举

- **日期**：2026-09-26
- **状态**：已采纳
- **背景**：多节点集群需要有人先建立成员集合。最初所有节点共用一条启动路径，都会把自己初始化成单节点集群——在单机部署下这是对的，在多节点部署下则是灾难：每个节点都成为一个独立的单节点集群，而且**永远不会合并**，因为它们各自都认为自己已经是一个完整的集群了。
- **考虑过的方案**：
  1. 所有节点都自举，靠后续的成员变更合并
  2. 由外部脚本通过客户端命令逐个引导（用 `RAFT ADD-NODE` 驱动）
  3. **一个节点带 `--bootstrap` 开关负责组建**，它按 `cluster.peers` 把其余节点逐个纳入；其余节点只启动、等待
- **决策**：方案 3，同时保留方案 2 的 `RAFT ADD-NODE` 供运行时扩容使用。
- **为什么选这个**：方案 1 有正确性问题——多个单节点集群之间没有「合并」这个操作，它们的日志各自独立，谁也不会让出主导权。方案 2 把「集群怎么起来」的知识放进了外部脚本，脚本一丢集群就无法重建；而集群拓扑是运维必须在配置里写明的东西，让二进制自己读它更不容易出错。方案 3 让「配置即拓扑」成立：写一份 TOML、标一个 `--bootstrap`，集群就起来了。
- **为什么不选其他**：方案 1 在原理上就不成立。方案 2 的问题不在于难做，而在于把必需的信息放在了一个无法被校验的位置——脚本里的节点列表与每个节点配置里的 `cluster.peers` 可能不一致，而且没有任何东西会报错。
- **后果**：
  - **整个集群里只能有一个节点带 `--bootstrap`**。带错多个会导致分裂出多个集群——这个错误目前靠「重复初始化被 openraft 拒绝」间接拦住
  - 组建过程中若某个节点始终起不来，引导节点会**启动失败**而不是降级成一个更小的集群。少一个节点却照常启动，等于把配置降级成建议
  - `--bootstrap` 必须对既有数据目录幂等：把 openraft 的「不允许重复初始化」当成启动失败，会导致集群只要落过盘就再也起不来
- **何时重新审视**：若需要支持「集群自发现」（如基于 DNS 或配置中心）时。

## ADR-015：快照策略可配置，日志靠快照截断

- **日期**：2026-09-26
- **状态**：已采纳
- **背景**：日志只能靠快照截断——只有已经被纳入快照的那部分才允许删除，否则一个落后的从节点没有办法靠日志追上来。早期的实现没有配置快照策略，openraft 的默认行为下日志会随写入无限增长，**磁盘迟早被吃满**。这不是性能问题，而是能不能长期运行的问题；而且它没有任何报错，只会在某天以「磁盘满了」的形式爆发。
- **考虑过的方案**：
  1. 用 openraft 的默认值（每 5000 条一次快照），不暴露配置
  2. 暴露两个参数：`snapshot_logs_since_last`（多久建一次）与 `max_in_snapshot_log_to_keep`（快照之外还留多少日志）
  3. 提供手工触发快照的管理命令（`trigger_snapshot`），由运维决定何时建
- **决策**：方案 2。默认值与 openraft 一致（5000 / 1000）。
- **为什么选这个**：这两个数直接决定磁盘占用与单次快照的开销，而合适的取值高度依赖写入速率与数据大小——写 10 MB/s 的实例与写 100 KB/s 的实例不该用同一个值。默认值保证「开箱不会吃满磁盘」，配置项保证「调得动」。方案 3 作为自动策略的补充是合理的，但它不能替代自动策略：运维忘了触发，磁盘一样会满。
- **为什么不选其他**：方案 1 把「会不会吃满磁盘」交给了一个我们控制不了、也无法解释给运维听的默认值。方案 3 把一件本该自动的事情变成了人的责任，且失败模式是静默的。
- **后果**：
  - 配置项增加两个；`redis.conf` 兼容层同步支持 `cluster-snapshot-logs-since-last` 与 `cluster-max-in-snapshot-log-to-keep`
  - 「落后多少条日志改用快照追赶」的阈值按「快照间隔 + 保留量」推导，保证需要快照的从节点真的会收到快照
  - `RAFT INFO` 增加 `snapshot_index` 与 `purged_index`，让截断进度可观测——否则运维无法回答「日志到底有没有在删」
  - 测试用「写入量翻倍、留存跨度不翻倍」来断言有界，而不是比对某个魔法常数
- **何时重新审视**：若引入多 Raft 组（分片），每组都需要独立的策略配置。

## ADR-016：不做确定性网络模拟，改用真实 socket 上的可开关有向边

- **日期**：2026-09-26
- **状态**：已采纳（**推翻**了立项计划里「用 `turmoil` 做确定性模拟」的安排）
- **背景**：立项时的测试策略有四层，第二层是「用 `turmoil` 做确定性模拟：选举、网络分区、节点重启，同 seed 可完整复现」，`turmoil` 也一直被列在 `dev-dependencies` 里。但实现推进到集群阶段后，它一行都没有被用上——依赖挂在清单上，测试却在用真实 socket。这个不一致必须有个了结：要么用起来，要么删掉并说明理由。
- **考虑过的方案**：
  1. 把 `turmoil` 接进来：让 `Node` 能在 `turmoil::sim` 里跑，用虚拟网络与虚拟时钟做确定性模拟
  2. 保留依赖但先不接，等有空再说
  3. **删掉依赖**，用真实 socket 造分区（每条有向边一个可开关的 TCP 闸门），并把结论写进这里
- **决策**：方案 3。
- **为什么选这个**：`turmoil` 的价值在于**可复现的随机交错**——它能把「同 seed 下必然重现」这个能力给我们。但要拿到它，代价是把 `src/` 里六处 `tokio::net` 换成 `turmoil::net`（`node.rs`、`server/listener.rs`、`server/session.rs`、`raft/rpc.rs`、`raft/network.rs`、`raft/forward.rs`），也就是**为了测试方便，在生产代码的主路径上插一层网络抽象**。这直接违反本项目的架构约定：真正有价值的分层应当来自职责边界（协议层不认识 Raft、服务层只关心连接与字节），而不是为了某个测试框架的接口形状。而 redb 内部用的是 `std::fs`，`turmoil::fs` 拦不住它——落盘仍是真实磁盘、真实 `fsync` 抖动，所以「完全确定性」本来也拿不到，只能拿到网络部分的确定性。
  更重要的是**收益已经被别的东西覆盖了**：`turmoil` 想覆盖的三件事现在都有真实 socket 下的测试——选举与主节点死亡（`tests/cluster.rs`）、**非对称网络分区**（`tests/partition.rs`，六条有向边各自可开关）、节点重启与靠快照追赶（`tests/snapshot_replication.rs`）。这些测试用的是真实的 TCP、真实的 redb 文件、真实的进程内 Raft，发现的是**真的会发生**的问题。
- **为什么不选其他**：方案 2 是最差的——一个从不被使用的依赖会持续暗示「这类测试已经做过了」，而实际上没有。这次就是因为去核对「`proptest` / `turmoil` 到底用没用」才发现两者都空挂着；`proptest` 于是补上了属性测试，`turmoil` 则在这里被明确否掉。
- **后果**：
  - `Cargo.toml` 的 `dev-dependencies` 现在每一项都真的在用
  - 失去的是「同一 seed 必然重现」。分区测试仍然是**真实但不确定**的：它断言的是性质（必须拒绝、必须不挂起、未提交的日志必须回滚），而不是某一条具体的交错序列。若将来遇到一个只在罕见交错下出现的缺陷、且反复复现不了，那时的选择是**针对那个缺陷**写一个最小的确定性测试，而不是先把整套网络抽象铺开
  - 分区的建模方式写进了 `tests/partition.rs` 的模块文档，包括「闸门关闭时接受连接后立刻丢掉、而不是不监听」这个关键选择——它决定了对端看到的是「连接被拒」（可重试）还是「发了但没回音」（结果未知）
- **何时重新审视**：出现「只在罕见交错下复现、且无法用真实 socket 稳定复现」的缺陷时；或者当集群规模、拓扑组合超出真实 socket 测试能覆盖的范围时。

## ADR-017：转发路径上的退避只用于「没能送达」，跟着主节点提示走不算重试

- **日期**：2026-09-26
- **状态**：已采纳
- **背景**：`Forwarder` 的尝试循环里原本有一个无条件的「每次重试前先睡 `RETRY_DELAY`（200ms）」。它的本意是给选举留时间，但作用范围错了：**从节点的第 0 次尝试必然是本地执行，而它必然得到 `ForwardToLeader`**——因为从节点本来就不是主节点。「跟着这个提示去访问主节点」于是也走进了「重试」分支，先睡满 200 毫秒。结果是**从节点上的每一次读写都固定多花 200 毫秒**。实测一次读 205ms；一个测试里 240 次从节点读花了 49 秒，修复后 0.33 秒。
- **考虑过的方案**：
  1. 把 `RETRY_DELAY` 调小（比如 10ms）
  2. 去掉退避，任何情况都立即重试
  3. **按「上一次尝试有没有把请求送到一个可用的目标」决定是否退避**：没送到（连接不上、或还不知道主节点是谁）→ 退避；收到了权威指路 → 立刻去
- **决策**：方案 3。
- **为什么选这个**：方案 1 只是把问题缩小，没有消除它——从节点的每一次读写仍然白付一次固定延迟，而且这个延迟还得大到能覆盖一次选举才管用，两者无法同时满足。方案 2 会在真正需要等选举的时候（集群没有主节点）变成空转重试。方案 3 把两种性质完全不同的情况分开了：「上一次尝试失败了」需要退避，「上一次尝试给出了权威答案、只是答案不是我」不需要——后者的下一步是确定的，等它只是在浪费延迟。
- **为什么不选其他**：方案 1 与 2 都没有区分这两种情况，因而必然在其中一边做错。
- **后果**：
  - 从节点上的单次读写回到毫秒量级。这不只是性能问题：**「客户端连任意节点都能读写」是本项目的卖点之一**，每次操作多 200 毫秒会让这个卖点在实际使用中难以忍受
  - 这个缺陷**不会让任何断言变红**——它只影响延迟，不影响正确性。因此专门补了一条盯**量级**的测试（`tests/cluster.rs::a_follower_does_not_pay_a_retry_delay`，比较中位耗时），并做了负向对照：把退避改回原样，它立刻报「读操作中位耗时 205.24ms」而失败
  - 循环里的 `backoff` 不在循环开头重置：每一条会回到循环顶部的路径都会重新给它赋值，其余路径一律直接返回。这一点写在代码注释里，因为它不那么显然
- **何时重新审视**：若引入客户端侧的重试或幂等令牌，转发路径的延迟预算需要重新评估。
